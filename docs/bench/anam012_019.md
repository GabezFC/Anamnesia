# ANAM-012 / ANAM-019 — medidas

Script: `docs/bench/anam019_bench.py N rotulo` (vault sintético de 60 notas, pipeline `baseline`, `persist=True`, jsonl ativo,
Windows, SQLite local, 3 execuções por modo, 200–300 buscas cada, 10 de aquecimento). `ANAMNESIA_GATEWAY_ASYNC_PERSIST=0` = síncrono, `=1` = write-behind.

## search() ponta a ponta (ms)

| modo | p50 (3 execuções) | p95 (3 execuções) |
|---|---|---|
| ANTES (síncrono, código original) | 52.7 / 40.8 / 49.4 | 70.8 / 60.0 / 79.2 |
| DEPOIS, síncrono (`=0`) | 39.2 / 52.9 / 40.9 | 69.6 / 73.6 / 74.6 |
| DEPOIS, write-behind (`=1`) | 44.3 / 39.7 / 49.0 | 73.0 / 68.1 / 70.9 |

Ruído entre execuções (±10 ms) é maior que o ganho: a persistência é pequena frente ao custo de retrieval neste corpus.
Sem regressão detectável do trace (contextvars + 2 chaves em metrics_json).

## Custo isolado de `_persist` (medido por wrapper, 310 chamadas)

| modo | p50 | p95 |
|---|---|---|
| síncrono | 1.05–1.08 ms | 1.77–1.88 ms |
| write-behind | 0.22–0.23 ms | 0.32 ms |

Ganho real ≈ 0.8 ms (−78%) por search() no caminho do request, mais o fsync/lock de SQLite que sai da frente quando há concorrência.
Drenagem de 310 runs no `close()`: ~1.2 ms. Todas as 310 runs presentes no DB nos dois modos.

Conclusão honesta: ANAM-019 entrega a garantia (fila + flush + atexit) e remove ~0.8 ms/busca; não muda p50/p95 de forma mensurável nesta máquina/corpus.
